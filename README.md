# Andrew's Claude Code and Cursor Skills

Personal plugin marketplace for Claude Code and Cursor. Skills for PRD/story planning, idea interviewing, code review, and code simplification. The same skills, agents, and MCP servers install in both tools.

## Skills

| Skill | Description |
|---|---|
| [feature-planning](skills/planning/feature-planning/SKILL.md) | Orchestrate PRD development end-to-end into Mike Cohn/Gherkin user stories, with optional `product-designer` discovery when input arrives light on context. Use when turning a feature or task into a written PRD plus development-ready stories, saved under `docs/`. |
| [implementation-planning](skills/planning/implementation-planning/SKILL.md) | Generate flow/sequence diagrams (AS IS/TO BE when changing existing behavior) and extract implementation details — classes/modules, interfaces, API contracts, code samples, data/schema changes, dependencies, non-functional requirements, observability, rollout, security — into one user_story_<N>.md at a time. Use after feature-planning has produced docs/<TAG>/user_story_*.md files. |
| [interview](skills/productivity/interview/SKILL.md) | Interview the user relentlessly about a plan, decision, or idea. Use when stress-testing thinking. |
| [understand-the-intent](skills/productivity/understand-the-intent/SKILL.md) | Interview the user until shared understanding, then write `docs/<slug>/intent.md`: original prompt, context, questions and answers, summary, structured shared understanding, and intent. Open assumptions only when the user chooses them. Writes in STE100 English or Linguagem Simples (pt-BR), per the user's language. |
| [grammar-review](skills/productivity/grammar-review/SKILL.md) | Review and correct text for grammar, spelling, and clarity in any language (English, Portuguese, Spanish, Italian, and others). Detects the language automatically and rewrites using that language's plain-language standard, keeping original tone and mood. Explicit call only (`/grammar-review`). |
| [product-interrogatory](skills/productivity/product-interrogatory/SKILL.md) | Product discovery (persona, flow, problem statement) via direct interview in this session, plus a QA left-shift testability pass on the synthesis. Sequential, no subagent — same result as `product-designer` + `qa-reviewer` without the parallel overhead. |
| [code-simplify](skills/code-reviewing/code-simplify/SKILL.md) | Simplify code for clarity without changing behavior. Process: set scope and a test baseline, understand first (Chesterton's Fence), find opportunities, apply one change at a time, verify, report. References loaded on demand: design ([A Philosophy of Software Design](skills/code-reviewing/code-simplify/references/philosophy-of-software-design.md), [The Pragmatic Programmer](skills/code-reviewing/code-simplify/references/pragmatic-programmer.md)) and language samples ([Go](skills/code-reviewing/code-simplify/references/go.md), [Ruby](skills/code-reviewing/code-simplify/references/ruby.md)), picked by project language. Adapted from [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills). Use when code works but is hard to read or maintain. |
| [security-analysis](skills/code-reviewing/security-analysis/SKILL.md) | Read-only security review of a diff, branch, or files. Process: one-page threat model, learn the repo's security patterns, detect candidates per attack-surface slice, then verify each candidate in a separate pass that tries to refute it. Reports only findings with source, sink, missing control, exploit scenario, and confidence of 0.8 or higher. Unverifiable items go to "Needs human check" (fail open). References loaded on demand: [OWASP Top 10:2025 questions](skills/code-reviewing/security-analysis/references/owasp-2025.md), [false-positive rules](skills/code-reviewing/security-analysis/references/false-positive-rules.md), and language sinks and samples ([Go](skills/code-reviewing/security-analysis/references/go.md), [Ruby](skills/code-reviewing/security-analysis/references/ruby.md)), picked by project language. Strategy evidence in [docs/research](docs/research/ai-code-review-strategies.md). Use when asking for a security review or "is this safe". |
| [static-analysis](skills/code-reviewing/static-analysis/SKILL.md) | Run the project's own linter and formatter on changed code in autocorrect mode, then fix every remaining violation by hand until the run is clean. Lint rules are never disabled: no suppression comments, no config edits, no "false positive" exits. Language references with commands, autocorrect options, rule classes, and a "My preferences" section: [Go](skills/code-reviewing/static-analysis/references/go.md), [Ruby](skills/code-reviewing/static-analysis/references/ruby.md). Strategy sources in [docs/research](docs/research/static-analysis-strategies.md). Use when asking to lint, run static analysis, or fix lint errors. |
| [test-analysis](skills/code-reviewing/test-analysis/SKILL.md) | Read-only review of test quality for a code change. Process: map each changed behavior to the tests that protect it, scan tests for smells and for tests weakened in the same change, run the tests in random order and repeated, then prove weak tests with a small diff-scoped mutation check in a separate git worktree. Reports only findings with evidence (surviving mutant, run result, or diff line). References loaded on demand: [test smells](skills/code-reviewing/test-analysis/references/test-smells.md), [mutation checks](skills/code-reviewing/test-analysis/references/mutation-checks.md), and language commands, smells, and mutation tools ([Go](skills/code-reviewing/test-analysis/references/go.md), [Ruby](skills/code-reviewing/test-analysis/references/ruby.md)). Use when asking if tests are good, weak, missing, or flaky. |
| [data-and-migration-analysis](skills/code-reviewing/data-and-migration-analysis/SKILL.md) | Read-only review of database migrations and data-handling code. Process: find the engine, version, table size, and deploy order first, run the project's existing safety tools as candidate generators, then check each migration for lock and rewrite risk, unsafe backfills, old/new code compatibility during a deploy (expand and contract), and reversibility, and each data change for missing constraints, races, transaction gaps, and writes that skip checks. Uses `strong_migrations`, `active_record_doctor`, `database_consistency`, Squawk, and Atlas when the project has them. Unverifiable items go to "Needs human check". References loaded on demand: [migration safety](skills/code-reviewing/data-and-migration-analysis/references/migration-safety.md), [data integrity](skills/code-reviewing/data-and-migration-analysis/references/data-integrity.md), and language tools and traps ([Go](skills/code-reviewing/data-and-migration-analysis/references/go.md), [Ruby](skills/code-reviewing/data-and-migration-analysis/references/ruby.md)). Use when asking "is this migration safe" or to review a schema change or data model. |
| [performance-analysis](skills/code-reviewing/performance-analysis/SKILL.md) | Read-only performance review of a diff, branch, or files. Process: learn which paths are hot and how big the data is, find the project's own performance tools (rubocop-performance, Bullet, Prosopite, golangci-lint performance linters, benchmarks, profilers) and run them read-only as candidate generators, trace each hot path, then prove each candidate with a measurement or a stated data size. A pattern alone is never a finding. Unmeasurable items go to "Needs human check". References loaded on demand: [performance checks](skills/code-reviewing/performance-analysis/references/performance-checks.md), [evidence gathering](skills/code-reviewing/performance-analysis/references/evidence.md), and language tools and traps ([Go](skills/code-reviewing/performance-analysis/references/go.md), [Ruby](skills/code-reviewing/performance-analysis/references/ruby.md)). Use when asking "is this slow", "will this scale", or to check N+1, query count, or memory. |
| [dependency-analysis](skills/code-reviewing/dependency-analysis/SKILL.md) | Review a project's dependencies for known vulnerabilities, supply-chain risk, maintenance and license health, and safe updates. Three modes: Review (default, dependency changes in the branch plus uncommitted files), Audit (whole tree, on request), and Fix (minimal patched version, on request). Maps each dependency to its exposure (request path, internal runtime, build and test), traces vulnerable transitive packages to the direct parent, reads new packages without running them, and uses the project's own scanners and update tools (govulncheck, bundler-audit, OSV-Scanner, Dependabot or Renovate config). Major bumps stop at a migration report and a confirmation. Never adds ignore entries to scanner config. References loaded on demand: [dependency checks](skills/code-reviewing/dependency-analysis/references/dependency-checks.md), [update playbook](skills/code-reviewing/dependency-analysis/references/update-playbook.md), and language commands and traps ([Go](skills/code-reviewing/dependency-analysis/references/go.md), [Ruby](skills/code-reviewing/dependency-analysis/references/ruby.md)). Flows adapted in part from [dependabot-triage](https://github.com/akshayrao14/git-practices/tree/main/skills/dependabot-triage) and [updating-npm-package](https://github.com/spencerpauly/awesome-cursor-skills/blob/main/resources/updating-npm-package/SKILL.md). Use when asking to review, audit, update, or fix dependencies, or "is this package safe". |
| [reliability-analysis](skills/code-reviewing/reliability-analysis/SKILL.md) | Read-only review of what happens when code fails. Process: build a short failure model (dependencies, who waits, delivery guarantee, process model), find the project's own tools (errcheck, wrapcheck, race detector, goleak, RuboCop Lint and thread-safety cops, resilience libraries, job runners) and run the linters read-only, check observability against Datadog (tracer setup, handled errors marked on spans, log and trace correlation, monitors, metric tags) and read Datadog data read-only when the MCP tools exist, then trace each failure path for swallowed or misreported errors, missing timeouts, unsafe retries, non-idempotent handlers and jobs, leaked resources, half-finished work, and failures nobody can see or debug. Concurrency checks (data races, goroutine leaks, thread safety) run only when the diff has a concurrency trigger. Every finding needs a failure scenario and a reproduced or traced path. Unverifiable items go to "Needs human check". References loaded on demand: [reliability checks](skills/code-reviewing/reliability-analysis/references/reliability-checks.md), [evidence gathering](skills/code-reviewing/reliability-analysis/references/evidence.md), [Datadog](skills/code-reviewing/reliability-analysis/references/datadog.md), and language tools and traps ([Go](skills/code-reviewing/reliability-analysis/references/go.md), [Ruby](skills/code-reviewing/reliability-analysis/references/ruby.md)). Rules drawn from the Google SRE book, the AWS Builders' Library, the Uber Go style guide, and the Sidekiq best practices. Use when asking "what if this fails", "is this retry safe", "can we debug this in production", or "is this thread-safe". |
| [complete-code-review](skills/code-reviewing/complete-code-review/SKILL.md) | Runs the code-reviewing skills on a change. Default scope is the branch against main plus the uncommitted work. Named files narrow it. "Whole project" widens it. Process: pick the skills from the file classes and content signals (security, harness review, dependency, data and migration, reliability, test, performance), run each in its own Opus agent at high effort (the parallel group at once, the skills that run code one at a time, performance last), check each finding against the real file, merge duplicates and conflicts by a fixed priority, then apply the verified findings in batches with a checkpoint for each, and run `static-analysis` last. Findings that change behavior, schema, data, or a major version wait for the user's decision. Unverified findings are never applied. Say "review only" to stop before any change. References loaded on demand: [routing](skills/code-reviewing/complete-code-review/references/routing.md), [agent prompts](skills/code-reviewing/complete-code-review/references/agent-prompts.md), and [snapshot, merge, and apply](skills/code-reviewing/complete-code-review/references/merge-and-apply.md). Use when asking for a full code review, to review a branch or the whole project, or to review and fix. |
| [harness-code-review](skills/code-reviewing/harness-code-review/SKILL.md) | Runs the current harness's own review and simplify tools on a change. Claude Code: the built-in `code-review` skill, then `simplify`. Cursor: the native `bugbot` and `security-review` subagents (the same reviewers as `/review`), then this plugin's `code-simplify`. Default scope is the branch against main plus the uncommitted work. Report only by default: `simplify` runs, and fixes are applied, only when you say "fix". Also runs as one lens inside `complete-code-review`, in a `code-reviewer` agent, review only. Codex is not supported yet. Use for a quick review with the native tools. Use `complete-code-review` for every lens. |
| [scan-pipelines](skills/continuous-integration/scan-pipelines/SKILL.md) | Read-only inventory of every quality check a project defines: lint, format, type check, tests, integration tests, coverage, SAST, secrets, dependency audit, migrations, containers, IaC, API contracts, and more. Process: detect the stack, read every source (CI configs with reusable workflows and includes, task runners, git hooks, tool configs, containers, bots, and branch protection through `gh api` GET), resolve each check to its real command with `file:line`, trigger, blocking status, services, secret names, and whether it runs locally, then report drift between sources and suggest missing checks that fit the stack, each with evidence, one tool, a priority, and an effort. Chat report only. Never runs a check, writes a file, or triggers remote CI. References loaded on demand: [sources](skills/continuous-integration/scan-pipelines/references/sources.md) and [check catalog](skills/continuous-integration/scan-pipelines/references/catalog.md). First of the `continuous-integration` family, followed by `build-pipelines`, `document-pipelines`, and `run-pipelines`. Use when asking what checks or pipelines a repo has, to audit CI, or which checks are missing. |
| [build-pipelines](skills/continuous-integration/build-pipelines/SKILL.md) | Set up every quality check of a project to run locally in Docker, the same way CI runs it. Process: preflight Docker and Compose, run `scan-pipelines`, ask once which suggested checks to add, plan an image per check (app image for checks that need the app runtime, pinned official image for standalone tools, a Dockerfile only when no image fits, each tag confirmed with `docker manifest inspect`), show the plan and wait for approval, then add one service per check to the project's existing compose file under the `pipelines` profile, with test services on `tmpfs`, cache volumes, secrets by `${VAR}` only, and an `x-pipelines` block holding the category, CI source line, full-suite command, changed-files command, file pattern, and triggers. Builds, pulls, and smoke-tests each service, and checks that `docker compose up` starts the same services as before. Never edits CI config, never changes an existing service, never weakens a tool config. References loaded on demand: [compose patterns](skills/continuous-integration/build-pipelines/references/compose-patterns.md) and [tool images](skills/continuous-integration/build-pipelines/references/tool-images.md). Run a check with `docker compose --profile pipelines run --rm <check-id>`. Use when asking to set up, dockerize, or containerize the checks, or to run CI checks locally. |
| [document-pipelines](skills/continuous-integration/document-pipelines/SKILL.md) | Write `docs/pipelines.md`, the guide to a project's quality checks, from the `pipelines` services that `build-pipelines` added to the compose file. Process: read the merged compose config with `--no-interpolate` (so no secret value is read), call `build-pipelines` first when no pipelines services exist, keep every human line outside the `<!-- pipelines:... -->` markers, then fill the managed sections: overview table, prerequisites (Compose version, secret names, network), one-time setup, how to run one check, the whole suite, or changed files, one section per check (what it protects, tool and CI version, image, CI source line, commands), checks that run only in CI, differences from CI, and a YAML manifest that `run-pipelines` reads. Every command is copied from an `x-pipelines` block, never invented. Never edits the compose file, CI, README, or CLAUDE.md. References loaded on demand: [doc template](skills/continuous-integration/document-pipelines/references/doc-template.md). Use when asking to document the checks or pipelines, or to refresh the pipelines doc. |
| [run-pipelines](skills/continuous-integration/run-pipelines/SKILL.md) | Run a project's quality checks locally in Docker, from the manifest in `docs/pipelines.md`. Default scope is the files changed in the branch and the staging area against main. Each check runs on its matching files (`{files}`, or `{dirs}` for Go packages), runs its whole suite when a trigger file (lockfile, tool config, test helper) changed, and is skipped when nothing relevant changed. Changed source files map to their tests. Say "full" for the whole suite, "fix" to also run checks that edit files, "fail fast" to stop at the first blocking failure. If the doc is missing it calls `document-pipelines`, which calls `build-pipelines` and `scan-pipelines` as needed. Checks that the manifest matches the compose services and refreshes the doc when it is stale. Runs every check one at a time, separates `fail` (findings) from `error` (could not run), removes only the services it started (never `docker compose down`), and reports each failure with the skill to fix it. Never edits code or config to make a check pass, never triggers remote CI. References loaded on demand: [selection rules](skills/continuous-integration/run-pipelines/references/selection.md). Use when asking to run the checks, the pipelines, CI locally, or to verify a branch before a PR. |
| [design-doc-mermaid](skills/design-doc-mermaid/SKILL.md) | Create Mermaid diagrams (flowchart, sequence, class, ER, state, C4, architecture) from text or code. Vendored from [SpillwaveSolutions/design-doc-mermaid](https://github.com/SpillwaveSolutions/design-doc-mermaid). |

## External dependencies

`feature-planning` depends on skills from [deanpeters/Product-Manager-Skills](https://github.com/deanpeters/Product-Manager-Skills) (marketplace: `pm-skills`). `allowCrossMarketplaceDependenciesOn` in `.claude-plugin/marketplace.json` only grants permission to reference that marketplace — it does not install it or its plugins. Each skill in `pm-skills` ships as its own plugin, so the marketplace and each plugin used here must be installed separately:

| Skill | Description |
|---|---|
| [prd-development](https://github.com/deanpeters/Product-Manager-Skills/tree/main/skills/prd-development) | Build a structured PRD connecting problem, users, solution, and success criteria. Drives Step 1 of `feature-planning`. |
| [user-story](https://github.com/deanpeters/Product-Manager-Skills/tree/main/skills/user-story) | Create user stories with Mike Cohn format and Gherkin acceptance criteria. Drives Step 5 of `feature-planning`. |

Install in Claude Code:

```
/plugin marketplace add deanpeters/Product-Manager-Skills
/plugin install prd-development@pm-skills
/plugin install user-story@pm-skills
```

Install in Cursor: Cursor has no cross-plugin dependencies, and `pm-skills` ships no Cursor plugin manifest, so copy the two skills into your user skills folder:

```
git clone --depth 1 https://github.com/deanpeters/Product-Manager-Skills /tmp/pm-skills
mkdir -p ~/.cursor/skills
cp -R /tmp/pm-skills/skills/prd-development /tmp/pm-skills/skills/user-story ~/.cursor/skills/
```

## Install

### Claude Code

Add marketplace:

```
/plugin marketplace add andrewhenriquef/personal-claude-plugin
```

Install plugin:

```
/plugin install andrew-skills@andrew-plugins
```

### Cursor

1. Open **Customize** in the sidebar, then **From GitHub Repository**.
2. Enter `andrewhenriquef/personal-claude-plugin`.
3. Install the `andrew-skills` plugin.
4. Optional: set `CONTEXT7_API_KEY` in **Plugins → Configure** for higher context7 rate limits. context7 works without it.

Generated Cursor agents rewrite Claude Code `Skill` calls into reading that skill's `SKILL.md`. Shared skills name `AskQuestion` and the Task tool where Claude Code uses `AskUserQuestion` and `Agent`. Agents use `model: inherit`. In Cursor, `feature-planning` Step 0 stays in the main thread, because a subagent cannot hold the discovery interview.

## Maintaining

The Claude Code files are the source of truth: `.claude-plugin/`, `.mcp.json`, and `agents/`. The Cursor files in `.cursor-plugin/` are generated from them. Never edit `.cursor-plugin/` by hand. After you change a Claude file, run:

```
python3 scripts/sync_cursor.py
```

`python3 scripts/sync_cursor.py --check` exits non-zero when the Cursor files are stale. The script maps the Claude `model` alias to a Cursor model (`MODEL_MAP`), marks an agent `readonly` when its `tools` list has no `Write`, `Edit`, or `Bash`, rewrites `Skill` tool calls in the generated agents, keeps marketplace entries to the fields the Cursor schema allows, and rewrites `${VAR:-default}` in `.mcp.json` to a Cursor plugin variable.
