# Doc template

The shape of `docs/pipelines.md`. Text in `<angle brackets>` is filled from the facts. Every managed section sits between a start and an end marker. A re-run replaces what is between the markers and keeps everything else.

Markers are HTML comments, so they do not show when the Markdown renders:

```
<!-- pipelines:<section>:start -->
...
<!-- pipelines:<section>:end -->
```

Sections, in order: `header`, `overview`, `prerequisites`, `setup`, `run`, `checks`, `ci-only`, `differences`, `manifest`.

People may write their own text between sections (for example a "Troubleshooting" part). Keep it.

## Template

````markdown
# Quality checks

<!-- pipelines:header:start -->
> Generated by `document-pipelines` from `<compose file>` on <YYYY-MM-DD>. Text between `pipelines:` markers is replaced on the next run. Write your own notes outside them.
<!-- pipelines:header:end -->

## Setup (once)

Pull the tool images and build the local ones:

```sh
docker compose --profile pipelines pull --ignore-buildable
docker compose --profile pipelines build
```

Run this again after a change to `<compose file>`, a Dockerfile in `docker/pipelines/`, or a lockfile.
<!-- pipelines:setup:end -->

<!-- pipelines:run:start -->
## Run

Ask your agent to run `run-pipelines`. By default it runs the checks on the files changed in your branch and staging area, compared with `main`. Say "full" to run the whole suite.

By hand:

```sh
# one check, whole suite
docker compose --profile pipelines run --rm <id> <full>

# one check, some files (checks that support it)
docker compose --profile pipelines run --rm <id> <changed with {files} shown as <files>>

# stop and remove the test services after a run (never `down`: it stops the app too)
docker compose --profile pipelines rm -sf <dependency services, for example db-pipelines>
```
<!-- pipelines:run:end -->

## Manifest

Read by `run-pipelines`. Generated from the `x-pipelines` blocks. Do not edit by hand.

```yaml
version: 1
generated_from:
  compose: <compose file>
  date: <YYYY-MM-DD>
checks:
  - id: <id>
    category: <category>
    source: <source>
    ci_version: '<ci_version>'   # or null
    blocking: <blocking>
    full: '<full>'
    changed: '<changed>'         # or null
    files: '<files>'
    triggers: [<triggers>]
    writes: <true / false>
    requires: [<VAR names>]
```
<!-- pipelines:manifest:end -->
````

## Filling rules

- Copy `full`, `changed`, and `files` exactly. In the manifest, quote `ci_version`, `full`, `changed`, and `files` in single quotes (double a single quote inside: `''`), and write `null` bare. Unquoted, YAML turns `ci_version: 1.10` into the number `1.1`, which never matches the compose string, so `run-pipelines` sees drift on every run. A command with ` #` or `: ` breaks or truncates.
- In the guide, show `{files}` as `<files>` and `{dirs}` as `<dirs>` so a reader sees they are placeholders. In the manifest keep `{files}` and `{dirs}`.
- `Blocks merge`: `required` → yes. `fails-job` → "fails CI, not required". `allow-failure` → no. `local-only` → local only.
- Leave out a table row or a bullet when its value is empty, except in the manifest, where every field is always present.
- Anchor links: GitHub makes `#<id>` from the `### <id>` heading. Keep ids lowercase with dashes so the links work.
